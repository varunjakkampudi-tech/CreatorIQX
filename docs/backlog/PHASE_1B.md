## Known gaps (recorded honestly, not hidden)

1. **No real-Postgres/Redis run of this module's stores or routes yet this session.** `SqlPlanStore`/`SqlVideoStore` are reviewed against the exact RLS/audit/outbox pattern already proven in `workspaces.infrastructure.sql_store` and `youtube.infrastructure.sql_connection_store`, and the route tests (P1B-05) exercise the full API-to-service path with in-memory/fake doubles standing in for the database - but nothing has yet run `plans`/`videos` through a live Postgres with RLS enforced. CI's `ci-python` job does run real Postgres/Redis service containers against the full suite including the RLS meta-test, so this gap narrows once that run is green (see P1B-06), but no dedicated integration test (the `tests/integration/` pattern `test_task_queue.py`/`test_rbac_db.py` use) was written for this module this session.
2. **A pre-existing gap in `youtube`/`intelligence`'s own SQL stores was found, not fixed, while building this module.** `SqlChannelConnectionStore`, `SqlChannelVideoStore`, `SqlRecommendationStore` and `RedisPostgresQuotaLedger`'s non-reservation reads never call `set_tenant_context` before querying - `quota_ledger.py`'s `reserve()` does, but its own earlier-reviewed reads do not, and neither do the other three stores' methods. Those tables are `FORCE ROW LEVEL SECURITY` with a `WITH CHECK` clause requiring `app.workspace_id` to be set, so an insert through `SqlChannelConnectionStore.save_connection` (for example) would be rejected by Postgres today, not just silently under-scoped. This was never caught because Phase 1A's own tests for these stores use fakes, not a real database, and no Phase 1A integration test exercises them against real Postgres either. `planning`'s own stores (this phase) call `set_tenant_context` on every method, including reads, so the new code does not repeat the bug. Fixing the three pre-existing stores is out of this phase's scope (not requested, and touching Phase 1A code mid-Phase-1B would blur the phase boundary) - flagged here as a real, specific, un-fixed defect for a dedicated ticket, not silently carried forward.
3. **Approval invalidation (`approved -> in_review` on a post-approval edit) has the domain edge but no trigger.** The transition graph already allows it (spec §3, ADR 0013 decision 4), but nothing in this phase causes it, since `publish_snapshots` and the edit-tracking it depends on do not exist until Phase 1D. Recorded as expected, not a defect.
4. **No video-board UI.** Spec §11 lists "Video Board (kanban of the state machine)" as a screen to build; this phase is backend-only (routes and services), matching how Phase 1A also shipped no frontend. The `GET /videos` response already carries everything a kanban view would group by (`status`), so the UI is additive, not a backend redesign, when it is built.
5. **Series/topic clustering (spec feature 4: "series and topic clusters, drag and drop") is reduced to a plain `series: str | None` label.** Drag-and-drop ordering and true clustering are UI/UX concerns with no backend counterpart yet; the field exists so a later UI has something to group by, without inventing backend structure (sort order, cluster entities) nothing has asked for yet.
