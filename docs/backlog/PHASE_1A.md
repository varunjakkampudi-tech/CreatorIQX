## Known gaps (recorded honestly, not hidden)

1. **P1A-03's literal "real channel" proof is owner-blocked.** Everything that can be built and automatically verified without a human in the loop has been: the OAuth provider, the Data API client, and every service that calls them are unit-tested against fakes that mirror the real Google/YouTube response shapes. The one thing no amount of autonomous work can do is click through a Google OAuth consent screen - that needs a real browser, a real Google account, and `YOUTUBE_OAUTH_CLIENT_ID`/`SECRET` configured in `.env` (same category as P0-052's real-login step, which was also owner-only). **Action needed from the owner:** create a YouTube-scoped OAuth 2.0 client in Google Cloud Console (separate from the login client, per ADR 0004), set `YOUTUBE_OAUTH_CLIENT_ID`/`YOUTUBE_OAUTH_CLIENT_SECRET`/`TOKEN_ENCRYPTION_KEY` (generate with `python -c "from creatoriqx_api.platform.crypto import generate_key; print(generate_key())"`) in `.env`, start the stack, and connect a real channel through the UI (or `POST /api/v1/youtube/connect` directly) once a Connect screen exists.
2. ~~Real-infrastructure verification has not run yet this session~~ **Resolved.** CI (`ci-python`, `ci-js`, `ci-docker`, `ci-security`, `codeql`, `docs`) is green on commit `ebaf55f` - see P1A-08's row above for the full account, including the four real defects CI's `mypy --strict`/`pytest` runs caught that this session's own sandbox (no device-bridge, no PyPI network access) could not have caught with `ruff` alone.
3. **No API-route-level tests yet** (`TestClient` against `youtube.api.connect`/`ingestion` and `intelligence.api.audit`) - the application-layer services behind every route are unit-tested with fakes, but the FastAPI wiring itself (dependency injection, response models, status codes) is not yet exercised end to end the way `test_auth.py` does for login. `ruff`/`mypy --strict`/`lint-imports` do confirm the wiring type-checks; still carried forward as a real test-coverage gap.
4. **ADR 0009's "reconciliation" step (rebuild the Redis counter from the Postgres ledger after a flush) is not implemented.** The live counter and the durable ledger are both written on every reservation, but nothing yet rebuilds Redis from Postgres if Redis is flushed mid-day - a workspace would simply get a fresh quota window early in that scenario (fails open, not closed, so it is not a security issue, just an honesty gap against the ADR's original text). Scoped out of P1A-04 for time; left as a documented follow-up, not silently dropped.
5. **No Celery integration test yet** for `youtube.ingest_channel`/`intelligence.run_audit` against a real embedded worker (the pattern `test_task_queue.py` established for `ops.ping`/`ops.flaky`). The services they call are unit-tested directly; the Celery task wrapper itself (argument marshalling, correlation-id logging) is reviewed but not integration-tested.
6. **No real-Redis/Postgres integration test exists yet for `RedisPostgresQuotaLedger`'s atomic Lua reserve-or-fail script or for the 5 new tables' RLS policies specifically.** CI's `ci-python` job does start real Postgres/Redis service containers and ran the full `pytest` suite (312 passed) with no marker filter, so the RLS meta-test (`tests/integration/test_rls.py`, which auto-discovers every `workspace_id` table) did exercise the 5 new tables for real. But `quota_ledger.py`'s own coverage in that same run was only 48% (`.data, 50, 63-66, 71-90` uncovered) - confirming no dedicated `-m integration` test was ever written against it this session; it is exercised only indirectly, through fakes, by `test_youtube_ingestion_service.py`. A real concurrency test (N parallel reservations never exceed the cap) is still only promised by P1A-04's acceptance test, not proven.
