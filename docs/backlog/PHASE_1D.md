# Phase 1D Backlog: QA, approval and YouTube synchronization

Spec scope (CLAUDE.md §15): "Pre-publish QA, approval diff, immutable publish snapshot, link or discover the YouTube video, capability model, metadata synchronization with read-back, drift detection, manual-apply fallback, idempotency and sync state." Done when: "One real video goes from idea through QA and approval to an immutable publish snapshot, is linked to a real YouTube channel using an allowed publishing path, and the approved metadata is successfully synchronized (verified by read-back). Where direct API media upload is restricted, the creator uploads the media manually in YouTube Studio as Private and links it. Direct `videos.insert` upload is an optional audited capability, not a Core dependency."

Every ticket's outcome is binary (PASS / BLOCKED / FAIL, spec rule 8). A PASS without evidence is invalid (spec §15 backlog-structure rule).

## Known gaps (recorded honestly, not hidden)

1. **`direct_video_upload`/`direct_publish` stay `requires_audit`/unverified by construction.** This phase never attempts `videos.insert`; the default workflow is manual Private upload + link, per ADR 0007. Verifying those two capabilities for real needs Google's compliance audit (OQ-01), out of scope for v1.
2. **No real YouTube write has been exercised against a live channel yet by this phase's own tests** - route tests use fakes, same shape as every prior phase's "no real-Postgres run" gap, now extended to "no real-Google-API-write run" as well. P1A-03 (once unblocked) gives us a real linked channel; a manual smoke test against it is the natural follow-up once P1D lands.
3. **Thumbnail capability (`thumbnail_update`) has no `thumbnail_variants` producer yet** - feature 6 (thumbnail) is Could-tier infrastructure-only in Core (template preview). This phase wires the capability and the sync path for it, but there is nothing upstream to populate a thumbnail asset for a snapshot until that tier is built. Snapshots carry a nullable thumbnail reference for this reason.
4. **Scheduling eligibility check depends on `remote_snapshots`' captured privacy/publication state being fresh.** If the creator changes the linked video's privacy in YouTube Studio between a capability check and the actual apply, the apply still re-reads before writing (ADR 0007 #5), but the *QA warning* shown earlier in the flow can go stale. Documented, not fixed - the authoritative check is always the one immediately before the write.
5. **`ApprovalService.invalidate_if_approved` exists and is unit-tested, but nothing calls it yet.** The spec's approval-invalidation rule ("any change to a publish-bound artifact after approval ... returns to `in_review`") needs `content`'s `ScriptService`/`MetadataService`/`ChapterService` to call this method after creating a new version on an approved video - a cross-module call from `content.application` into `publishing.application`, which did not exist before this phase and is not wired yet. Tracked here rather than silently left undone; the next natural ticket once P1D-05's routes exist to exercise it end to end.
6. **`YoutubeSyncService.resolve_drift`'s `adopt_remote`/`overwrite_remote` modes move the link back to `pending_sync` but do not yet perform the actual content change** (creating a new local metadata version from the remote fields, or re-running `apply_snapshot`) - that orchestration belongs to the API layer once P1D-05's drift-resolution route exists, so it can decide what "a new local version that goes through review and approval" means at the HTTP boundary. `ignore` is fully correct today (stays flagged, never silently cleared).
7. **Only the `metadata_update` capability is wired into `apply_snapshot`.** `thumbnail_update` and `scheduling` are modeled in the domain (`SyncFieldGroup`, `Capability`) but `YoutubeSyncService` does not yet attempt them - consistent with Known gap 3 (no thumbnail producer) and the fact that `MetadataFields.publish_at` is always passed as `None` for now. P1D-04/05 extend this once the real write client exists.

## Cross-reference

ADR 0015 (new): building snapshots from "current" version ids without pointer columns on `videos`, and treating `youtube_capabilities` as a global non-tenant table.
